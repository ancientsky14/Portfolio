## What it is

eTracker is the internal system a regional bureau office uses to know where any
document is right now — who has it, how long they have had it, and what has to
happen next before it moves on.

A document entering the office moved between divisions on paper. The authoritative
record of where anything was lived partly in a logbook, partly in a spreadsheet, and
partly in the memory of whoever had handled it last. Answering "where is this
application right now" meant asking people.

## Constraints

- **Procurement reality.** Fixed budget, and the system had to be something the office
  could keep running without a line item for a vendor retainer.
- **No dedicated IT staff.** Whatever got built had to be operable by the records
  officer, not by a developer.
- **Personnel movement.** Regional office staff rotate. A system that depends on one
  champion is a system with an expiry date.
- **Deployment freedom.** The office needed to be able to host it where their own
  policy allowed — which is why it ships as a container rather than assuming one PaaS.

## What I built

A Next.js 16 application over Supabase, with Postgres row-level security doing the
access control rather than application-layer checks — so a query that shouldn't return
a row can't, regardless of which route asks.

Packaged with a Dockerfile using Next's `standalone` output, which keeps the runtime
image small and means the office can deploy it to whatever infrastructure they are
allowed to use, rather than being pinned to a single platform.
